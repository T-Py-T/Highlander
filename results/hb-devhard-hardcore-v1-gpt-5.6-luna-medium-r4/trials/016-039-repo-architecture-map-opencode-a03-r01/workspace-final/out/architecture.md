# minisvc Architecture

## Overview

`minisvc` is a small Python service with a framework-neutral HTTP adapter and a CLI bootstrap command. The implementation is authoritative over the older README design notes.

## Modules

- `minisvc.cli` is the active console startup module. It loads settings, constructs `OrderRepository`, initializes the schema, and prints readiness.
- `minisvc.config` defines `Settings` and reads `MINISVC_DB` and `MINISVC_READONLY`.
- `minisvc.models` defines the `Order` dataclass.
- `minisvc.storage.repo` owns SQLite schema setup and order CRUD.
- `minisvc.api.routes` registers `POST /orders` and `GET /orders/<order_id>`.
- `minisvc.api.handlers` performs payload-to-model conversion and repository calls.
- `minisvc.audit` creates event dictionaries returned by handlers; it is not an audit store.

The empty `minisvc/api/__init__.py` and `minisvc/storage/__init__.py`, plus the small `minisvc/__init__.py` export declaration, are package marker/metadata files, not business-logic modules.

## Entry Points

The `minisvc` console script maps to `minisvc.cli:main` in `pyproject.toml`. HTTP integration starts by calling `minisvc.api.routes:register_routes`. That function binds the POST and GET paths to `create_order` and `get_order`.

## Data Flow

At CLI startup, environment values become `Settings`, a repository is created, and `init_schema` creates the `orders` table. For `POST /orders`, the handler requires `order_id`, `customer`, and `total_cents`, converts the amount with `int()`, constructs an `Order`, and calls `repo.save`. The response includes an event generated by `order_event`. `GET /orders/<order_id>` calls `repo.get`, then returns either a missing response or the order's `__dict__` plus a read event.

There is no application object or HTTP server in this fixture; the external adapter supplies `app.post` and `app.get`.

## Storage

SQLite is opened directly for every repository operation. The path is `MINISVC_DB`, defaulting to `orders.sqlite` in the process working directory. The only schema is `orders(order_id primary key, customer not null, total_cents not null)`. Connections use context managers, so successful writes commit, but there is no migration/versioning layer, retry wrapper, audit table, or transaction spanning an order write and an audit write.

## Runtime Flow

The important create flow is: route registration -> POST dispatch -> payload indexing and `Order` construction -> SQLite insert -> in-memory event construction -> response. `MINISVC_READONLY=1` currently changes only a settings value; it is not passed to the repository or checked by any write path.

## Risks and Extension Points

- Storage durability and concurrency are delegated to default SQLite behavior; there is no backup, migration, busy timeout, or retry policy.
- Duplicate order IDs and other SQLite errors propagate from `save` rather than becoming a defined API error response.
- Audit events are response data only. Add a persistent audit repository and an explicit transaction policy if auditability is required.
- Configuration has a readonly flag that is presently ineffective and parses only the exact string `1` as true.
- Input validation is limited to required dictionary keys and `int(total_cents)`; empty strings, negative totals, and business constraints are not rejected.
- The route lambdas and framework-neutral `app` interface are simple extension points for an HTTP framework, request validation, and error mapping.
